# 抽奖姬 2.3.1：发布与升级指南

开发者：想吃金丝虾球  
仓库：https://github.com/csudmj/bili-danmaku-lottery

## 使用新增功能

- 视频页选择弹幕 / 评论。评论范围默认仅主评论，另可包含全部楼中楼或仅指定主评论下的回复。
- 视频起止时间按本机时区的发布时间筛选；结束留空时点击抽奖会刷新名单，以点击时刻截止。空关键词表示发言即可参与。
- 新版更新检查超过 45 秒会明确提示并允许重试；这个修复不能追溯修改尚未升级的旧版，旧版卡住可重启后检查或手动安装。


- 主界面右上角打开“关于 / 更新”，查看开发者、版本号和仓库二维码。点击仓库、Issue 或 PR 按钮会使用系统浏览器打开对应页面。
- 安装版启动后自动检查正式版本，之后每四小时检查一次，也可手动检查。发现更新后按钮会提示；点击下载，完成后选择安装并重启。下载不会打断当前活动。安装前必须停止收集并确认；当前活动不会恢复；每个模块最近 20 轮历史、专属权重名单、登录会话与背景保留。
- ZIP 版提供手动下载入口，不覆盖运行中的文件。不具备内置更新功能的旧版需手动安装当前版本，以后才可使用程序内更新。
- 主界面及竖向小窗的“自动滚动”开关独立保存。名单溢出时上下往返，边缘停留两秒；手动滚轮或按下鼠标后暂停五秒，操作名单中的控件时暂停。人数不足一屏时保持静止。
- 软件遇到部分运行异常或界面加载失败时，会暂停收集并显示建议。在“关于 / 更新”中可导出不含 Cookie、账号昵称和弹幕内容的诊断信息。
- 若双击 EXE 完全打不开，请在安装目录双击“启动检查.cmd”。检查工具核对发行文件的 SHA-256，列出缺失、改变或无法读取的文件，并把报告保存在系统临时目录。它用于检测文件损坏，不代替数字签名，也不能覆盖所有系统问题。

## 手动更新 GitHub 源码

1. 解压本次提供的“GitHub源码上传包”。进入解压目录，确认能直接看到 `package.json`、`README.md`、`electron`、`src`、`shared` 等文件或文件夹。
2. 打开仓库首页，点击 **Add file → Upload files**。
3. 将上述目录中的内容拖入上传区，保留文件夹结构。不要上传源码 ZIP 本身，也不要额外包一层文件夹。注意隐藏的 `.github`、`.gitignore` 等文件也应上传。
4. 等待全部上传完成。提交说明填写 `Release 2.3.1`，点击 **Commit changes**。
5. 同路径文件会替换；网页上传不会删除旧文件。请上传完整源码包。若 GitHub 提示文件数量或大小限制，分批上传，保持相对目录一致。完整上传后检查 README 显示 2.3.1，并检查 `shared/project.ts` 的仓库地址。
6. 不上传 `node_modules`、`dist`、`dist-electron`、`.build-cache`、`release`、备份、个人登录数据或真实弹幕样本。提供的源码包已排除这些内容。

## 发布 2.3.1 Release

在仓库 **Releases → Draft a new release**：

1. Tag 输入 `v2.3.1` 并创建，Target 选已更新源码的分支（通常 `main`）。
2. 标题填写 `抽奖姬 v2.3.1`，说明可使用根目录 CHANGELOG.md 中的 v2.3.1 段落。
3. 上传同一次构建产生的四个附件：
   - `bili-danmaku-lottery-2.3.1-x64.exe`：推荐用户下载的安装版。
   - `bili-danmaku-lottery-2.3.1-x64.exe.blockmap`：更新所需的差分信息。
   - `latest.yml`：更新描述文件，必需。
   - `bili-danmaku-lottery-Windows-x64-v2.3.1.zip`：可选的完整免安装版。
4. 等待附件上传完毕。不要改名或手工修改 `latest.yml`，不要混用不同构建的附件；其中的文件名、大小及 SHA-512 必须与安装包对应。
5. 发布为正式版本，不勾选 Pre-release，并设为 Latest。确认后点击 **Publish release**。草稿或预发布不会作为本软件的稳定更新。
6. V2.2.1 是采用新应用标识的更新基线，需要首次安装，不迁移旧版数据和安装登记。后续版本使用 V2.2.1 安装版测试“发现新版 → 下载 → 停止收集 → 确认安装 → 重启”。ZIP 版不执行自动安装。发布前的本地测试不能代替这一步。

仓库必须保持公开且用户网络能够连接 GitHub。没有 Release、附件缺失或网络不通时，程序显示检查失败建议，不会把它当作已是最新版本。

## 后续发布

可执行 `pnpm run verify:release` 检查发行包，`pnpm run export:github` 生成源码与附件上传目录。

先在 `package.json` 递增版本，并同步界面版本及文档；执行测试与 `pnpm run build:win`。从对应 `release/v版本号/` 上传新的安装包、blockmap、latest.yml 以及可选 ZIP。Tag 与程序版本保持一致，避免重复发布相同版本号。更新只在用户确认后安装，不会在直播过程中自行重启。

## ICU 报错排查

`Invalid file descriptor to ICU data received` 表示 Chromium 没有获得有效的 ICU 数据文件描述符。单凭此日志不能断定原因，也不能排除打包或系统兼容问题。建议先用新安装包重新安装，或将 ZIP 完整解压到新文件夹；不要只传 EXE。运行启动检查，重点查看 `icudtl.dat` 是否存在、完整且可读。检查系统是否隔离文件，无需关闭安全防护。若文件检查通过但仍打不开，请在 Issue 提供软件版本、Windows 版本、检查报告及现象。

程序界面启动前发生的底层故障无法由应用内弹窗捕获；独立启动检查用于这一情况。检查报告由用户自行提交，软件不会自动上传。

## 清理仓库旧文档

网页上传只新增或覆盖文件，不会删除旧文件。更新源码时，请在 GitHub 的 main 分支删除旧版 PDF 和各版本独立发布说明（包括 `docs/抽奖姬_v1.4.0_图文使用说明.pdf`、`docs/v1.5.0发布说明.md`，以及若已上传的 `docs/v2.2.1发布说明.md`）。历史变更统一保留在根目录 `CHANGELOG.md`。历史 Release 保留，便于旧版更新测试与回退。
